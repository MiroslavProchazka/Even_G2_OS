# Phone history and conversation preparation (0.4.0)

Continuous mode defaults to **Answer every utterance**. Two seconds of silence still finalize speech. Completed answers stay in a bounded, memory-only phone history of 20 entries after the lens hint expires or capture pauses. Each entry contains the final transcript, full returned answer, optional compact cue, mode and timestamp. Expand an entry to read it; export JSON (with a selectable fallback) or delete the history. Reloading/closing loses it. Demo and real history are separate. This is conversation content, deliberately separate from metadata diagnostics. Export is explicit; there is no automatic upload or persistent archive.

**Prep notes** hold up to 1,500 characters of people, topic, goal and background for the active continuous session. Apply while paused. Applying resets the model's rolling context, but not the phone history. Notes go to the selected model with each finalized utterance; they are not sent to speech recognition or written to diagnostics/localStorage. Notes and the current utterance must fit the 4,000-character chat request limit; oversized combinations report an error rather than silently truncating speech.

**Contextual cues · experimental** asks the selected model whether it has a useful new explanation, suggested answer or next step. The model may return `show:false`; that turn remains in the rolling conversation context without generating a lens hint or history entry. A shown cue requires a validated JSON object with a hint of at most 120 characters and a fuller detail string. Raw JSON never streams to the glasses. Invalid/oversized output is reported as an error, not displayed as a malformed hint. This is model judgement, not a claim of reliable intent classification. Evaluate it on real conversation before relying on silence as a meaningful decision.

The short hint appears on the glasses with the existing SDK-confirmed ten-second lifetime. Detail appears in the current phone answer and history. The ordinary direct mode still streams text and uses the static three-line lens viewport; overflow is marked with an ellipsis. The full provider response remains in phone history, but the app does not invent missing detail if the model itself answered briefly.

Both direct Beast and gateway chat support the cue-format instruction. Deploy the updated gateway when using that transport. This does not require or assume provider-native JSON schema support; the client validates returned text. The local synthetic demo includes an explicitly labelled canned contextual cue and is not an accuracy test.

Validation: unit/integration tests cover defaults, input limits, structured cue validation, preservation of quiet turns, no JSON leakage, bounded history, expiry/pause retention, exports/deletion, and both API system prompts. Hardware layout and real-model cue quality remain device tests.
